# Task EP-01: Feature contracts and sync architecture

Branch: `feat/ep-01-contracts`. Epic file: `docs/superpowers/plans/EP-01-contracts.md`. This is the critical path: every later epic that stores data depends on what you settle here. No new dependencies.

## Objective

Specify and prove, in code and tests, how optional features add versioned, mergeable records to the existing profile document, how optional modules default to off, and what a server-side provider adapter must guarantee. Keep the existing profile representation and all existing behaviour unchanged.

## Deliverables

1. **Inventory (no code change).** In `docs/product/DATA_CONTRACTS.md`, document from the real code: how the profile `S` is serialized and persisted (`store/useStore.js`, `lib/mobile.js` nativeSave), the stamp model (`_ts`, `_f`, `edited`, PER_KEY) in `lib/sync-merge.js` and `api/sync-stamps.js`, the 409 flow in `lib/api.js` and `api/server.js`, backup/export/import paths, module switches (`lib/modules.js`), and how `api/integrations/` stores provider credentials. Include a state diagram (mermaid) and a table of extension points and restrictions.
2. **Answer these with tests, not prose:**
   - What happens to an unknown top-level key of `S` and to an unknown key inside a known collection when (a) the current server merges, (b) the current client merges on a 409, (c) a backup is exported and imported, (d) the MCP server reads and `log_workout` saves? Write characterization tests that pin today's behaviour. If unknown fields are dropped anywhere, that is the key finding: document it and propose the smallest fix.
   - Does `lib/modules.js` allow a module that is off until someone turns it on? Today a missing key means on. New optional modules (nutrition, activity, insights, camera, sensors, anatomy, automation and so on) must be **off by default** without changing any existing module's behaviour or any existing profile.
3. **Contracts.** In `DATA_CONTRACTS.md`, define the canonical record contract that EP-04 (nutrition) and EP-07 (activities) will use: collection key, `schemaVersion`, record id (UUID), creation source, per-field stamps and tombstones in the existing stamp model (do not invent a second mechanism), units, provenance (`source`, external id, content fingerprint), day and timezone rule, idempotency key for imports, and one authority plus one conversion direction per external system. Add JSON fixtures under `frontend/src/lib/__fixtures__/contracts/` (or the nearest existing fixtures convention) for a nutrition entry, an activity and a provider link, including a tombstoned record and a record from an older schema version.
4. **Proof tests before any core change (RED must show a real unsupported behaviour).** Two-device cases for a generic id-keyed collection: add/add, add/edit, edit/edit on different fields, edit/delete, delete/re-add, replay of the same change (idempotent), merge order does not matter (commutative), merging three devices in any order converges, an older record missing a field, restore of an older backup, id collision. Mirror the cases on the API side.
5. **Minimum extension hooks (only what the proofs need).**
   - A small generic helper for id-keyed optional collections that reuses the existing merge machinery, on both sides (`lib/sync-merge.js` and `api/sync-stamps.js`) with the parity test extended.
   - A default-off flag for modules in `lib/modules.js` (for example `optIn: true` on the module entry, read by `isOn`), with tests that every existing module and every existing profile behaves exactly as before. Do not add the new modules themselves; later epics add their own entry.
   - If unknown fields are dropped somewhere, the smallest safe preservation fix, with tests.
6. **Provider security interface.** In `DATA_CONTRACTS.md`, the contract every server-side adapter in `api/integrations/providers/` must meet, derived from the existing providers: fixed or operator-configured base URL with allowlist and SSRF rules, sealed per-user credentials, timeouts, bounded response size, rate limiting, no secret in logs, explicit availability status (never a fake "connected"), idempotency, revoke. Add a reusable test helper or checklist test if one fits the existing test style.

# Task EP-04: local-first nutrition diary

Read `docs/superpowers/briefs/WAVE-2-common.md` first. Epic outline:
`docs/superpowers/plans/EP-04-diary.md`. The data rules are already decided and tested in EP-01:
`docs/product/DATA_CONTRACTS.md` ("Canonical records for EP-04 and EP-07", "Deliberate add-back
ownership", "Retention, reset and prefer rules"). Build on them. Do not invent a second merge,
clock or deletion mechanism.

## Approved scope

A food diary you can use with no server and no third party: add, edit, delete and undo food
entries per day and meal, see honest daily totals, and have every entry survive reload, offline,
two-device sync, backup export/import and an older client.

Decisions already taken by the orchestrator:

- **Module:** `{ id: 'nutrition', group: 'body', optIn: true }` in `lib/modules.js`, following
  `docs/MODULES.md`. Off by default. Off hides every surface and never deletes data.
- **Storage:** `S.nutritionEntries`, the collection EP-01 registered. Records follow the EP-01
  contract (`schemaVersion: 1`, UUID v4 id, `createdAt`, `createdBy`, `source`, `day`, `timeZone`,
  `occurredAt`, `label`, `amountG`, `energyKcal`, `proteinG`, `carbohydrateG`, `fatG`, `_f`,
  `_ts`). The key must not appear in a profile that never used the diary.
- **Reads go through `visibleOptionalEntries(S, 'nutritionEntries')` only.** Never render or total
  the raw array.
- **Additions to the record you may make** (document each in `DATA_CONTRACTS.md` and the
  fixtures): a meal slot (`meal`: breakfast, lunch, dinner, snack), and the serving the user typed
  when it was not grams (label, count and the grams or millilitres per serving), so the saved
  amount can be explained later. Nutrients stay amounts for the saved entry, not per 100 g.
- **Unknown is not zero.** A nutrient the user did not enter is omitted. Totals show the sum of
  what is known and say how many entries have no value for that nutrient.
- **Day filing:** the entry keeps the local `day` and IANA `timeZone` chosen when it was logged.
  Travel or a later timezone change never refiles a saved day.
- **Delete and undo:** delete is a tombstone that keeps the row. Undo is the deliberate add-back
  recipe from `DATA_CONTRACTS.md` (negative deletion stamp, unchanged field clocks).
- **No saved-foods library in this task.** "Search" means your own earlier entries: recent and
  frequent foods derived on read from the visible entries, picked to prefill a new entry. A
  separate food library would be a new registered collection and is a follow-up.
- **No daily targets, no CSV export, no Coach or MCP knowledge of the diary, no new bottom tab.**
  The diary is reached from a compact Home tile shown only while the module is on, plus the place
  where Body screens are already listed. Propose the exact entry points after inspecting how
  Measurements is reached.
- **No server lookup in this task.** A separate task (EP-05a) builds an Open Food Facts lookup
  route on the server. Keep one seam for it: provenance fields (`source`, `externalId`,
  `contentFingerprint`) that are set at creation survive later edits untouched.
- No API route should be needed: the profile already syncs. If you find you need one, stop and
  report.

## Deliverables

1. `docs/superpowers/plans/EP-04-tasks.md` and the contract additions, with updated fixtures under
   `frontend/src/lib/__fixtures__/contracts/`.
2. Pure helpers in `frontend/src/lib/nutrition/` (each with a test beside it): validation and
   normalization of an entry (ranges, units, UUID, schema version; an unknown newer
   `schemaVersion` is kept and shown as unsupported, never rewritten), serving arithmetic, day
   grouping, totals with unknown counts, recent foods, and the create, edit, delete and undo
   reducers that produce correctly stamped state.
3. Store wiring in `store/useStore.js` kept thin, through the existing `update` and stamp path.
4. Tests before UI:
   - calculations: grams, millilitres and servings; zero versus missing; rounding; invalid,
     negative, non-finite and huge values; edit keeps provenance; delete by id.
   - sync through the real store and merge: add/add on two devices, edit/edit on different and on
     the same field, edit/delete, delete then undo against a concurrent edit, offline then
     reconnect with a 409, reset, `prefer`.
   - backup: JSON and ZIP export then import through the real reader, including a deleted entry
     staying deleted and a restore bringing entries back.
   - older client: a client that does not know the collection round-trips it unchanged; a profile
     from before the diary gains no key.
   - parity: anything touched in `lib/sync-merge.js` is mirrored in `api/sync-stamps.js` with the
     parity test. Prefer not to touch either.
5. `views/Nutrition.jsx` (thin) with components under `components/nutrition/`: day selector, meals
   with their entries, add and edit sheet (label required; amount, energy, protein, carbohydrate
   and fat each optional), recent foods, daily summary, delete with undo. Use the EP-02
   primitives (`MetricCard`, `Skeleton`, `ErrorState`). 44 by 44 px targets, visible focus,
   labelled inputs, no colour-only status, works at 320 px, RTL and 200 percent text.
6. Route `/nutrition` gated by `isOn(S, 'nutrition')`, the Modules page entry, the Home tile, and
   `docs/MODULES.md` updated. Locale keys in every pack, in a new Nutrition block at the end of
   the module-related keys (another task adds Stats keys elsewhere in the same files).
7. Browser evidence under `docs/superpowers/evidence/EP-04/`, synthetic profile only: module off
   shows nothing; enable; add, edit, delete, undo; reload; offline add then reconnect against a
   real local api with a throwaway `DATA_DIR`; two browser profiles editing the same account;
   backup export, wipe, import. Screenshots at 320, 390 and 1280 px, dark and light. Console
   errors and failed requests listed. A workout can still be logged with the module on and off.
8. Bundle: the diary loads as its own lazy chunk. Report the entry chunk delta against
   `docs/product/BASELINE_REPORT.md`; it must be near zero.

## Acceptance

- Every diary action survives reload, offline, a 409 merge, export/import and restore.
- No duplicate and no resurrected entry in the two-device matrix, in both merge orders.
- Totals reconcile by hand with the entries of a fixture day; unknowns are counted, not zeroed.
- Module off: no diary surface anywhere, data untouched, all existing suites green.
- Legacy profile serialization is byte-identical when the diary was never used.
